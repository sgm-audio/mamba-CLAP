# Claims verification: the two plans and this repository

**Audit date:** 2026-10-04 (UTC)  
**Repository revision at audit start:** `2d38ff6`  
**Scope:** Plan A (ship a conventional audio plug-in first, then use it to win specialist work) and Plan B (fine-tune/adapt Mamba-3 with LoRA on rented GPUs and ship audio plug-ins/adapters). This report distinguishes general research results, implementation evidence, and business estimates.

## Executive verdict

- **Plan A is the lower-risk strategy, not a validated business forecast.** Shipping a small, reliable effect and using it as a portfolio piece is sensible. The proposed rate bands, project values, scarcity of JUCE contractors, and side-income timeline are hypotheses, not evidence-backed expectations.
- **Plan B is technically plausible as an R&D direction but overstates the jump from sequence-model complexity to a real-time audio product.** Mamba-family models have favorable sequence scaling; that does not establish audio quality, bounded callback time, a supported Mamba-3 LoRA/export route, or low cloud cost.
- **This checkout does not demonstrate either plan end to end.** It contains upstream Mamba-3 research code, a separate simplified C++ SSM, a TorchScript/LibTorch CLAP experiment, and another incomplete plug-in architecture. They do not form one verified train → export → load → real-time process pipeline. There are static build blockers, and the published “production ready” statements exceed the evidence.

## 1. Technical claims in the plans

| Claim | Assessment | What is actually supported |
|---|---|---|
| Full self-attention scales quadratically with sequence length; Mamba-family methods scale linearly. | **Supported, narrowly.** | The Transformer paper gives `O(n²d)` per-layer self-attention cost; the original Mamba paper presents linear sequence-length scaling for its selective SSM/scan. This is an asymptotic sequence-cost comparison, not a prediction that a Transformer plug-in will necessarily glitch. Buffer size, model width, caching, implementation, hardware, and the callback deadline all matter. [1](https://arxiv.org/html/1706.03762v7) [2](https://arxiv.org/pdf/2312.00752) |
| “O(1) inference” means a Mamba-3 effect is real-time safe. | **Misleading.** | A recurrent step can be independent of the *number of prior sequence positions* while still doing substantial work determined by hidden width, state size, layer count, and model operations. At 48 kHz, a 64-sample host block is only 1.33 ms for the whole plug-in chain. That budget has to be measured on the target CPU. RTNeural is an example of a specialized, allocation-conscious audio inference engine; it does not certify arbitrary PyTorch/TorchScript inference as real-time safe. [1](https://ccrma.stanford.edu/~jatin/rtneural/) |
| Mamba-3 is a continuous-time-invariant SSM that can be fine-tuned as an audio effect. | **Incorrect as phrased / unproven for audio.** | The Mamba-3 paper and upstream implementation are real research artifacts, but the checked-in implementation forms input projections for `B`, `C`, time-step and other quantities; the source does not support describing the implemented block as simply time-invariant. The paper is not evidence of a trained audio-effect model, plug-in, or low-latency CPU kernel. The upstream repository also has specialized kernel/dependency requirements. [1](https://arxiv.org/abs/2603.15569) [2](https://github.com/state-spaces/mamba) |
| Mamba state automatically means a useful “60+ second musical memory.” | **Unsupported promise.** | A fixed-size recurrent state can be carried indefinitely, but that is not equivalent to retaining useful information for a specified number of seconds. Effective memory depends on learned dynamics, representation, hop rate, and task. In this repo the default audio trainer uses 4,096 waveform samples at 44.1 kHz—about 93 ms per training sequence—not a demonstrated 60-second task. |
| LoRA/PEFT makes a Mamba-3 adapter pipeline straightforward. | **Possible in principle; not verified here.** | Hugging Face documents PEFT/LoRA examples for its Mamba and Mamba-2 implementations. That is not proof that the upstream Mamba-3 module, its custom kernels, a particular target-module selection, TorchScript/ONNX export, and a C++ run-time adapter switch all work together. A plug-in must also load/swap adapter weights off the audio thread and test the adapter’s effect on latency and output. The repository search found no LoRA training, adapter serialization, or RunPod worker integration. [1](https://huggingface.co/docs/transformers/model_doc/mamba) [2](https://huggingface.co/docs/transformers/model_doc/mamba2) |
| A small LoRA file can simply be injected into a shipped base model. | **Incomplete.** | Low-rank updates can be compact, but size depends on rank, target matrices, layers, and precision. The host still needs a compatible model, a defined adapter format, deterministic loading, validation, and a safe way to select/swap weights. “Small adapter” does not itself solve inference cost, model compatibility, or audio-thread safety. |
| RunPod provides a cheap, nearly turnkey fine-tuning product. | **Partly true; the price promise is conditional.** | RunPod provides GPU Pods and Serverless workers; the customer still needs to build the container, training job, data flow, checkpoints, storage, and failure handling. Its official page showed RTX 4090 pricing of $1.10/hour for Serverless and $0.74/hour for a Pod when checked (pricing changes). Three full billable minutes at $1.10/hour is **$0.055**, already above five cents; three minutes at $0.74/hour is about $0.037, before storage/start-up/other charges. So “under $0.05” can be true under some configurations, but is not a general guarantee. [1](https://www.runpod.io/pricing) |
| “A 24 GB GPU is enough,” or “A100/H100 is required.” | **Model-dependent estimate.** | Neither is universally true. Batch size, sequence length, precision, model dimensions, optimizer states, and kernel support determine fit and throughput. The plans need an actual timed, memory-measured training run for the chosen model and data. |
| JUCE provides VST3, AU, AAX, and CLAP “out of the box.” | **CLAP part is outdated/incorrect as of this audit date.** | JUCE’s published format list includes VST/VST3, AU/AUv3, AAX, and LV2, but not CLAP. JUCE announced CLAP support for JUCE 9, while its July 2026 announcement still described AudioProcessor v2—the foundation for the CLAP-specific work—as in progress for follow-up releases. The official CLAP developer guide still points JUCE users to the CLAP JUCE extension. AAX also has a separate Avid SDK/commercialization process. [1](https://juce.com/features/) [2](https://cleveraudio.org/developers-getting-started/) [3](https://juce.com/blog/juce-roadmap-update-q3-2025/) [4](https://forum.juce.com/t/juce-9-is-available-now/69175) [5](https://developer.avid.com/aax/) |

## 3. What this repository actually contains

### Separate code paths—not one integrated product

1. **Vendored upstream Mamba-3:** `mamba/mamba_ssm/modules/mamba3.py` contains the Mamba-3 PyTorch module and specialized kernel calls. This is research/model source, not a C++ audio runtime. The local `mamba/mamba_ssm/__init__.py` exports only `__version__`, so the README’s `from mamba_ssm import Mamba3` convenience import is not provided by that file as checked. PyTorch is absent here, so no import or kernel execution was verified.
2. **MambaDAW custom C++ SSM:** `MambaDAW/src/mamba_layer.cpp` implements its own recurrence. `MambaDAW/tools/simple_mamba.py` explicitly says its `B` and `C` are fixed learned parameters, not input-dependent selective Mamba parameters. This is a small recurrent SSM prototype, not the upstream Mamba-3 implementation.
3. **Separate TorchScript CLAP experiment:** `clap-plugin/src/clap-plugin.cpp` loads a TorchScript module and calls Torch operations in `processAudioBlock()`. Pre-allocating a few input tensors does not remove temporary tensor operations, per-step argument/state vectors, or the TorchScript call from the host callback. `MambaWrapper::getInitialState()` returns an empty state, and its effect decoder layers are initialized with random weights in the constructor. The code therefore does not demonstrate a trained, hard-real-time Mamba-3 effect.
4. **Another plug-in architecture under `plugin/`:** the tree contains a `PluginCore` path and a separate `MambaFXPlugin` CLAP path, but important implementation files are absent. `plugin/CMakeLists.txt` names missing sources including `model/MambaInferenceEngine.cpp`, `dsp/STFTEngine.cpp`, `dsp/OverlapAddSynthesizer.cpp`, and `core/TransportState.cpp`; default ARA/UI options also name absent sources. `PluginCore::activate()` starts the inference engine but does not call its `set_audio_ring()` or `set_stft_engine()` methods; `run_dsp()` does not pop `result_queue_` or apply inference output. The separate `plugin/clap/MambaFXPlugin.cpp` implements basic gain/compression/saturation and has no model-engine member. Comments describing the intended architecture are not proof of the missing path.

### MambaDAW training/export does not match its plug-in model

- `MambaDAW/tools/train_audio_mamba.py` describes a synthetic reverb task, constructs `SimpleMambaModel(d_model=1)` by default, and trains 4,096-sample sequences by default (`sample_rate=44100`). That is roughly 93 ms of waveform per sequence. The processor constructs `MambaModel(N_MEL, ...)`—80-dimensional mel frames by default—at `MambaDAW/src/plugin_processor.cpp:73`. The default trainer/export therefore does not match the plug-in model dimensions or representation.
- The older `MambaDAW/python_training/train_mamba.py:79–82` explicitly sets `ssm_out = gated_out` in place of the state-space recurrence; it is not evidence of a trained Mamba SSM.
- `MambaDAW/tools/export_weights.py:115–118, 189–198` says the C++ loader supports FP32 only; its INT8 export path currently falls back to FP32. The README’s claim that quantization is mandatory and available via `-DENABLE_QUANTIZATION=ON` is contradicted by the exporter and CMake. Root `AGENTS.md` also says that CMake flag does not exist.

### Build, tests, and real-time evidence

- **Static build blocker in MambaDAW:** `MambaDAW/src/plugin_processor.h:9` unconditionally includes `inference_thread.h`, but that header is absent from the checkout. The processor constructs and calls `InferenceThread`/`MambaInferenceEngine` (`plugin_processor.cpp:69–74, 352–354`); CMake only treats `src/inference_thread.cpp` as an optional source and cannot supply the missing header. This is a likely compile blocker regardless of the tests below.
- **Additional static build blockers:** `plugin/CMakeLists.txt` references multiple missing `.cpp` files as listed above. The MambaDAW default GUI configuration points at `../JUCE/modules`, which is also absent in this checkout. `clap-plugin/CMakeLists.txt` requires LibTorch.
- **Real-time claims conflict with the code/docs:** `README.md:75–82` says there are no background threads and inference runs directly in the audio thread, while MambaDAW’s processor enqueues mel frames to an `InferenceThread`. Conversely, `clap-plugin/src/clap-plugin.cpp:232–304` runs Torch/STFT/model work inside the callback. In `plugin/clap/MambaFXPlugin.cpp:202–207`, reset allocates a new `EffectApplicator` and the source itself warns reset may be called on the audio thread. `docs/THREADING_AND_BUFFERING.md` asserts about 133 ns/sample but the audit found no reproducible benchmark record specifying hardware, model dimensions, or the tested binary.
- **“Production readiness” documents are not test results:** `PRODUCTION_READINESS.md` (now `docs/PRODUCTION_READINESS.md`, rewritten) claimed Mamba-3 integration, real-time safety, and tests; `FINAL_IMPLEMENTATION_SUMMARY.md` names `test_stft.cpp` and `test_plugin_integration.cpp`, which are absent from `clap-plugin/` in this checkout.
- **What was actually run:** at the initial audit revision, the standalone `MambaLayer` test compiled with `g++ -std=c++17 -O2 -Wall -Wextra -Wpedantic -IMambaDAW/src` and printed seven passes, but its harness could return success after a failed case and its block-vs-sample test used independently randomized layers. That test harness has since been corrected in the working tree: cases return booleans, failures produce a non-zero exit, and block-vs-sample uses identical deterministic weights. The corrected seven-case test was rerun and passed. It remains a narrow layer test; it does not validate a plug-in build, CLAP host behavior, model quality, Mamba-3, LoRA, or real-time deadlines.
- **Environment limits:** full CMake/Ninja configuration/build was not run because neither tool is installed; Python model execution was not run because PyTorch is absent. This report distinguishes those environment limits from the static missing-file findings.

## 4. Bottom line and recommended proof gates

1. **Choose one plug-in implementation and make it build first.** Remove/implement the missing CMake sources and headers; add a clean CI build and a host/CLAP validation run.
2. **Choose and name the actual model accurately.** Either call the current C++ layer a fixed-parameter SSM prototype, or port/integrate a specific Mamba/Mamba-3 block and verify every operation and state tensor. Do not badge the custom layer as Mamba-3.
3. **Create one matched train → export → C++ inference contract.** Train at the exact representation and dimensions used by the plug-in, add checkpoint format/version validation, and compare Python and C++ outputs on identical inputs and states.
4. **Keep general-purpose Torch inference off the audio callback.** If using a worker, wire the ring buffers and results all the way through, define stale-result/overrun behavior, and keep audio output bounded and useful while inference lags.
5. **Measure rather than infer real-time safety.** Test worst-case callback time, allocations, locks, resets, multiple instances, sample rates, and small host blocks on target CPUs; run actual DAWs and CLAP validation. A 133 ns/sample note or linear-complexity statement is not enough.
6. **Demonstrate effect quality and buyer demand separately.** Use paired/appropriately licensed audio, objective comparisons plus blind listening, a packaged demonstrator, then validate rates and recurring demand through scoped paid work.

Until those gates pass, describe the repository as **research/prototype code**, not a production-ready Mamba-3/LoRA real-time audio plug-in or proof of a reliable freelance income stream.
